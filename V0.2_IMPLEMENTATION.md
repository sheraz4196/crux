## Implemented behavior and compatibility

- Native commands remain untouched by default. Bash/Zsh `--enhance-commands` is explicit and skips existing aliases/functions; PowerShell native wrappers are deliberately unavailable because internal pipeline routing is ambiguous. Existing private helpers remain callable.
- Integration does not change PATH. Supported opt-in requests require terminal stdin/stdout; options, pipes, redirection, stdin and non-regular cat operands retain native behavior. Existing native-command aliases/functions are tested with default and opt-in installation.
- `--keep-prompt` preserves an existing prompt framework; default prompt replacement is explained before confirmation. `crux_restore_prompt` restores captured prompt state without overriding a user-owned helper. Reopen after uninstall or upgrading v0.1 blocks.
- Public listing/tree/Git commands reuse working handlers. Config get/set/reset validates the existing schema, preserves unrelated parsed TOML and supported comments, refuses unsafe layouts, and atomically writes; reset-all confirms unless `--yes` is supplied.
- All five v0.1 theme palettes and source viewing remain. Theme config updates use the shared atomic config editor. `general.terminal_palette` controls prompt OSC writes; `--reset-terminal` disables writes and requests emulator defaults only on interactive output.
- Guarded GNOME recovery records verified owned colors and restores only color keys from the original backup, resetting originally unset keys. It refuses newer color changes or unverified legacy state, preserves unrelated newer preferences, and disables prompt palette reapplication. Backups remain.
- Doctor retains its existing JSON fields and adds installation/profile/marker/support/GNOME checks and manual guidance. It does not repair or write anything.
- Listing/tree JSON has a documented version-1 schema, raw JSON-escaped filenames, entry metadata, tree depth/caps/errors and symlink boundaries.
- Installer reuses existing valid environments instead of recreating read-only activation files; refuses incomplete/symlinked environments and unrelated executable files/links before installing. Integration remains backed up, atomic and narrowly removable.

A final error-output regression check found that failure/warning messages could pass embedded terminal controls through ordinary errors. Shared error handling, config warnings and theme warnings now escape those controls; a regression test covers missing paths, invalid keys and malformed theme values.

## Commands

Added public `crux ls`, `crux tree`, `crux git status`; listing/tree accept `--json`. Added `crux config get KEY`, `set KEY VALUE`, `reset [KEY] [--yes]`; inspection text/JSON still works. Added theme `--reset-terminal` and `--restore-profile`; `crux theme NAME` and `--sync-profile` remain. Install/init accept `--keep-prompt` and `--enhance-commands`. Doctor accepts explicit `--shell`/`--profile`. Hidden init/prompt/render helpers are retained.

## Platforms and remaining acceptance

Actually tested: Linux; Python 3.14.3 full suite and fresh-wheel checks; Python 3.12.3 fresh-wheel smoke/timings; GNU Bash 5.3.9 including pseudo-terminal stdin/stdout; local Git repositories and disposable profiles. GNOME sync/restore is covered by mocked subprocess/state tests, not a live desktop. Zsh/PowerShell and macOS/Windows were unavailable locally. The existing CI matrix remains Ubuntu/macOS/Windows × Python 3.11/3.14 and now adds fresh-wheel smoke checks, POSIX installer verification, and recorded timing artifacts; no remote CI run/results are claimed.

Manual acceptance remains: real Zsh/PowerShell and OS matrix runs, GNOME desktop/profile recovery, emulator OSC reset behavior, keyboard interrupts, history, completion and full interactive job control. See `ACCEPTANCE.md`. Fish/cmd integration and PowerShell native wrappers remain unsupported. Prompt composition with arbitrary frameworks is not attempted; use `--keep-prompt`. Config editing refuses layouts it cannot preserve. Palette reset requests emulator defaults, not captured arbitrary earlier runtime colors. GNOME recovery is multiple key writes: a mid-operation failure can be partial and requires preserving backups and manual inspection. No automatic restoration occurs on exit or uninstall.
